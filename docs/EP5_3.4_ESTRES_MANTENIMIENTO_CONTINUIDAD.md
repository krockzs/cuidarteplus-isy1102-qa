## Método (límites y protección)

Se reutilizó el escenario JMeter del 3.3: cada hilo hace \`POST /autenticacion/login\` con cuenta ficticia y \`GET /pacientes\` con JWT transitorio en memoria. Cinco etapas secuenciales, dos ciclos por usuario y ramp progresivo: **1, 4, 8, 16 y 24 usuarios**, hasta 212 solicitudes HTTP sintéticas.

**Cortes automáticos:** si se observa al menos 20 % de errores, GET p95 mayor de 14 segundos, falta de respuesta de la API o 85 segundos en una etapa, no se aumenta la carga. Estas protecciones permiten observar degradación sin convertir el ejercicio en una prueba de indisponibilidad ilimitada.

**Observabilidad real:** latencia por operación, promedio, p95, errores, CPU y memoria residente del proceso API, conexiones observadas en PostgreSQL, huellas y conteos de registros clínicos sintéticos antes y después.

| Huellas después del reinicio de API | **Sin cambios** |

| Respaldo PostgreSQL 17 restaurado en una **base separada** | **Sí**, contenido coincidente |
| Duración de la restauración de base sintética | **100,04 ms** |

Las verificaciones protegen el conjunto de pacientes, usuarios y exámenes ficticios. Las acciones de login añaden eventos de auditoría y, por diseño, **no se exige** que la tabla de auditoría permanezca inmutable. El respaldo temporal fue eliminado antes de publicar el artefacto.

**RTO y RPO:** el tiempo observado para reiniciar la API es **una medición de recuperación del componente**, no un RTO extremo a extremo. La recuperación íntegra de una copia de base ficticia **no establece un RPO de producción**: no hubo pérdida de transacciones críticas ni fallo integral. Como hipótesis de planificación sujeta a validación de responsables se propone **RTO ≤ 15 minutos y RPO ≤ 5 minutos** para una futura plataforma de salud; esas cifras **no son** resultados medidos ni mandatos normativos.

## Análisis comparado de alternativas

| Estrategia | Ventaja | Riesgo / evaluación |
|---|---|---|
| Reactiva, reparar después de incidentes | Menor inversión inicial | **No recomendada**: permite persistir fuga clínica, contraseñas claras y pérdida de integridad |
| **Mantenimiento continuo basado en riesgos** | Prevención temprana, regresión automática y controles medibles | **Recomendada**: exige responsables y recursos, utiliza CI/CD implantado |
| Reescritura integral inmediata | Podría renovar arquitectura | Alto costo y riesgo de introducir nuevas regresiones; no sustituye pruebas de autorización |

**Periodicidad propuesta:** CI (Jest, Selenium, auditoría dependencias y controles de seguridad) en cada PR; JMeter semanal en staging; recuperación de respaldos mensual; revisión trimestral normativa, de requisitos y de objetivos de continuidad; verificación extraordinaria tras incidentes.

**Condición para entrega segura:** no promocionar software con exposición de datos clínicos, fallos de integridad o criterios obligatorios incumplidos. Los cambios de la tabla son **propuestas de una versión futura**; el caso de estudio original permanece sin corregir.

## Trazabilidad normativa y límites

- **Ley 19.628:** protección de datos personales; la prueba T-02 evidencia riesgo de exposición clínica y la propuesta busca prevenir accesos indebidos.
- **Ley 20.584:** contexto de reserva y resguardo de fichas clínicas.
- **Ley 21.719:** reforma al régimen chileno de datos personales y sus disposiciones de vigencia/transición deben verificarse al implementar. **Al 22-11-2026** existe una iniciativa legislativa relativa al aplazamiento de su entrada en vigor; consultar siempre la versión oficial de la Biblioteca del Congreso Nacional.
- **ISO/IEC 25010** e **ISO/IEC/IEEE 29119:** calidad y trazabilidad de pruebas. Su uso no implica certificación formal.

## Conclusión para IE7

Se ensayaron controles de rendimiento, degradación, telemetría y recuperación con medidas reales y guardas de seguridad. **La API no se cayó dentro de la carga observada; sí mantuvo una latencia de 5 segundos y no superó la condición de calidad.** Se conservaron los datos ficticios, se recuperó la API y se restauró un respaldo en una base independiente. La mejor opción de mantenimiento es **preventiva/correctiva continua y priorizada por riesgo**, con compuertas CI/CD, controles de seguridad, respaldos comprobables y objetivos de continuidad formalmente definidos antes de cualquier producción.
